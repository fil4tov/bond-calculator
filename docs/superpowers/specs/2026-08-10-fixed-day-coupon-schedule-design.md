# Фиксированные купонные периоды

## Контекст и причина изменения

Текущий backend строит купонные периоды календарными месяцами от даты размещения и
сохраняет исходный день месяца. Это не соответствует предоставленным графикам MOEX:

- выпуски с 12 выплатами используют непрерывные периоды ровно по 30 дней;
- ОФЗ с двумя выплатами использует регулярные периоды по 182 дня;
- первый период ОФЗ может быть нестандартным: в предоставленном примере он длится
  203 дня, а все последующие — 182 дня;
- регулярная часть графика привязана к дате погашения, а не к числу месяца даты
  размещения.

Из-за календарного сдвига текущий график уже со второго периода расходится с биржей.

## Цели

- Строить график фиксированными интервалами в днях, как в предоставленных данных MOEX.
- Поддерживать нестандартный первый период.
- Автоматически определять продолжительность периода по частоте выплат, если точное
  значение пользователю неизвестно.
- Позволить указать точную продолжительность периода вручную.
- Сохранить правила переноса выплаты на рабочий день, определения доступного купона,
  прогресса, выплаченной суммы и статусов облигации.
- Не удалять существующие облигации и покупки.

## Не входит в изменение

- Импорт полного графика с MOEX.
- Хранение каждого купонного периода отдельной строкой в БД.
- Купоны с изменяемой ставкой или разной суммой по периодам.
- Амортизация номинала, оферты и досрочное погашение.

## Модель данных и API

В `bonds` добавляется `coupon_period_days SMALLINT NOT NULL` с ограничением
`1 <= coupon_period_days <= 366`.

Миграция заполняет существующие строки по `payments_per_year`:

| Выплат в год | Купонный период |
|---:|---:|
| 12 | 30 дней |
| 6 | 61 день |
| 4 | 91 день |
| 3 | 122 дня |
| 2 | 182 дня |
| 1 | 365 дней |

После заполнения колонка становится обязательной. Существующие портфели не очищаются.

`POST /api/portfolio/bonds` принимает необязательное поле
`coupon_period_days`. Если поле отсутствует, сервис подставляет значение из таблицы.
В ответах карточки возвращается фактически сохранённое значение
`coupon_period_days`.

Значение должно быть целым числом от 1 до 366. Несовместимое с датами и вычисленным
числом выплат значение возвращает `validation_error` для `coupon_period_days`.

## Построение расписания

### Число купонов

Число периодов вычисляется по ожидаемой частоте выплат за срок обращения:

```text
period_count = max(
  1,
  round_half_up(
    (maturity_date - placement_date).days
    * payments_per_year
    / 365
  )
)
```

Округление выполняется по правилу `ROUND_HALF_UP`, а не банковским округлением Python.

Это даёт 36 периодов для обоих предоставленных трёхлетних ежемесячных выпусков и
32 периода для предоставленной ОФЗ.

### Границы периодов

Регулярная часть строится назад от даты погашения с шагом
`coupon_period_days`:

```text
последний endPeriod = maturity_date
предыдущий endPeriod = следующий endPeriod - coupon_period_days
```

Для всех периодов, кроме первого, начало равно окончанию предыдущего периода.
Начало первого периода всегда равно `placement_date`; поэтому первый период может быть
длиннее или короче регулярного шага.

Если рассчитанное окончание первого периода не позже даты размещения, входные данные
считаются несовместимыми и создание облигации отклоняется.

Расписание не материализуется целиком при построении карточки. `_period_at` вычисляет
границы нужного индекса арифметикой дат, а бинарный поиск ближайшего периода сохраняется.

### Выплата и владение

- `pay_date` остаётся первым рабочим днём начиная с `period_end`.
- Купон считается выплаченным при `pay_date <= today`.
- Покупка участвует в купоне только при `purchase_date < period_end`.
- Сумма ближайшей выплаты рассчитывается по количеству покупок, доступных на
  `period_end`.
- В день фактической выплаты ближайшим становится следующий купон.
- Статусы `active`, `payment_pending`, `matured` сохраняют текущее значение.
- `period_days` в API содержит фактическую длину периода. Для нестандартного первого
  периода она может отличаться от `coupon_period_days`.
- `elapsed_period_days` и прогресс рассчитываются по фактическим границам периода.

## Frontend

В форму добавления облигации рядом с частотой выплат добавляется необязательное числовое
поле «Купонный период, дней».

- После выбора частоты форма подставляет рекомендуемое значение из таблицы.
- Пользователь может изменить значение вручную.
- Используются существующие парсер и live-валидация целых числовых полей.
- В запрос уходит сохранённое значение; для совместимости API также умеет вычислить
  значение, если старый клиент поле не прислал.
- В detail-модалке отображается «Купонный период: N дней».
- Компактная карточка не получает дополнительного текста.

Прогресс и даты продолжают использовать поля `next_coupon` и не требуют нового
клиентского расчёта расписания.

## Миграция существующих данных

Новая Alembic-миграция:

1. добавляет nullable-колонку `coupon_period_days`;
2. заполняет её через `CASE payments_per_year`;
3. добавляет check constraint;
4. переводит колонку в `NOT NULL`.

Для текущей «СамолетP16» значение станет равным 30, после чего её график автоматически
сдвинется на биржевые границы без изменения покупок.

## Ошибки и совместимость

- Невалидное ручное значение возвращает существующий `422 validation_error` с
  `field_errors.coupon_period_days`.
- Клиент сопоставляет ошибку с полем формы.
- Старые клиенты, не передающие поле, продолжают работать благодаря серверному выводу
  значения из `payments_per_year`.
- Формат `next_coupon` и правила денежных расчётов не меняются.

## Тестирование

Backend-тесты фиксируют:

- оба ежемесячных MOEX-примера как непрерывные периоды по 30 дней;
- ОФЗ: первый период 203 дня и последующие периоды по 182 дня;
- вычисление периода для каждой допустимой частоты;
- ручное значение, серверное значение по умолчанию и валидацию диапазона;
- переносы `pay_date`, eligibility покупки, paid total, прогресс и статусы;
- сохранение индексной сложности без материализации полного графика;
- миграционный backfill без удаления облигаций и покупок.

Frontend-тесты проверяют автоподстановку, ручное редактирование, сериализацию,
server field error и отображение значения в detail-модалке.

E2E создаёт облигацию с 30-дневным периодом и проверяет ближайшие границы, совпадающие
с предоставленным биржевым графиком.

## Ограничение точности

Без полного биржевого графика невозможно гарантированно восстановить произвольные
нерегулярные выпуски. Предлагаемая модель точно воспроизводит предоставленные примеры и
поддерживает обычный постоянный купон с одним нестандартным первым периодом. Для
плавающих и нерегулярных графиков позднее потребуется хранение полного расписания.
